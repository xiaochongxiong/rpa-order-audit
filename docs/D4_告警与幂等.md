# D4 — 异常告警与指纹幂等

> 目标：把 D2 审核 + D3 对账产生的异常**自动汇总成一条告警**推送飞书，并保证**重跑不重复轰炸**。
> 这是项目三的最后一块工程拼图：D1 数据进出 → D2 审单分流 → D3 对账 → **D4 告警 + 幂等**。
> 完成 D4，项目三就覆盖了"人工 SOP 改造成系统自动执行 + 人处理异常"的完整闭环。

---

## 一、D4 做什么（先看懂再搭）

前三步把异常都算出来了，但**没人盯着看**。D4 补上最后一环：

1. **汇总**：从两张结果表里捞出所有异常，合成一条人能读懂的消息；
2. **告警**：推到飞书群，让相关人员第一时间看到；
3. **幂等**：同一批异常重跑时不重复推送——这是"工程实现"和"玩具脚本"的分水岭。

### 异常口径（11 条，实测）

| 来源 | 类型 | 数量 | 业务含义 |
|---|---|---|---|
| D2 审核结果 | 自动拦截 | 3 | 已冻结，禁止发货 |
| D2 审核结果 | 转人工 | 5 | 进人工队列核对 |
| D3 对账结果 | 金额不符/账单缺单/订单缺单 | 3 | 需财务核对 |

消息按这三类分组，每条带**订单号 + 商品 + 命中规则**（或差异金额），追责到单。

## 二、指纹幂等：原理（重点）

### 为什么需要

RPA 流程可能被**重复触发**：定时任务重跑、人手动补跑、失败重试……如果每次都推飞书，同 11 条异常会被轰炸 N 次，群里很快没人看了。

### 怎么做（三步）

1. **算指纹**：把"会改变告警语义"的字段（订单号 + 判定 + 命中规则）**排序后拼接**，加上日期和发送模式，算 md5：
   ```
   fingerprint = md5(日期 || 模式 || 排序后的异常清单)
   ```
   - 排序是必要的：否则表格行序抖动会被误判成"新内容"；
   - 模式（dry/real）纳入指纹：演练和真发互不干扰，切换时能正常补发。
2. **存标记**：处理成功后把 `{指纹, 时间, 状态, 各类数量}` 写入 `data/alert_state.json`。
3. **重跑比对**：新指纹 == 上次指纹 → **跳过推送**；内容变了（新单/改判/改金额）→ 指纹变化 → **自动重发**。

### 三态语义（诚实说明，别踩坑）

| 状态 | 是否更新指纹 | 含义 |
|---|---|---|
| `ok`（真发成功） | ✅ 写 | 这批已通知到位，重跑跳过 |
| `dry_run`（演练） | ✅ 写 | 这批已"演练处理"，重跑跳过；切真发时因模式变化会重发 |
| `failed`（真发失败） | ❌ 不写 | 没通知成功，下次可补发——**绝不能写指纹，否则异常被永久吞掉** |

> 这条"失败不写指纹"是幂等设计的关键：幂等防的是**重复**，不能防成**漏发**。

## 三、飞书推送（复用项目一经验）

代码沿用项目一 `notify.py` 已验证的两条工程经验：

- **四态结果**：`ok` / `failed` / `skipped_no_webhook` / `dry_run`，跳过原因分开记，便于排障；
- **退避重试**：网络异常最多 3 次尝试（间隔 1s / 3s）；飞书业务码非 0 属配置问题，**不重试**。
- **失败不崩主流程**：推送失败仅打印日志、落盘消息文件，不影响已算好的审核/对账结果。
- **webhook 不硬编码**：从项目一 `ecom-daily-report\.env` 读取 `FEISHU_WEBHOOK`（代码不打印、不提交）。

默认 `SEND_REAL = False`（演练模式）：只落盘 + 打印，**不真发**，不打扰你的飞书群。想真发时把代码 CONFIG 区的 `SEND_REAL` 改成 `True` 重跑即可。

## 四、影刀操作步骤

沿用 D2/D3 验证过的模式：**贴一条「插入代码段(Python)」即可**，无需配任何变量映射。

1. 确认前置：`data/审核结果_D2.xlsx`、`data/对账结果.xlsx` 都在（D2/D3 已生成）；
2. 新建 PC 自动化应用 → 自定义搭建；
3. 拖一条「**插入代码段(Python)**」；
4. 打开 `docs/D4_自包含代码.py`，**全文复制**粘贴到代码区 → 确定 → 运行。

### 完成标志

控制台打印 11 条汇总消息（拦截 3 / 转人工 5 / 对账差异 3），末尾显示 `推送结果: dry_run`；`data/` 下生成 `告警消息.txt`。**再跑一次**，应打印"幂等跳过：异常内容与上次一致，不重复推送"。

### 真发（可选，需你主动开）

1. 把代码 CONFIG 区 `SEND_REAL = False` 改成 `True`；
2. 确认项目一 `.env` 里 `FEISHU_WEBHOOK` 有效（复用现有群）；
3. 重跑——因模式纳入指纹，真发不会被演练的指纹挡住；
4. 去飞书群确认收到 11 条汇总消息。

## 五、三档划分（按学习需要分配精力）

| 档位 | 内容 | 要求 |
|---|---|---|
| **必须懂** | 为什么重跑要幂等；指纹怎么算（排序拼接 + md5）；为什么失败不能写指纹 | "重复执行怎么办"是常见工程问题，这是工程意识的核心证据 |
| **知道即可** | 四态结果区分；退避重试（1s/3s，业务错误不重试）；webhook 从 .env 读不硬编码 | 能说出"推送失败不影响主流程、有重试兜底"即可 |
| **直接跳过** | md5 具体实现、urllib 请求体拼装、state 文件读写细节 | 实现细节，不影响讲清设计思想 |

## 六、卡住了自查

| 现象 | 先看这里 |
|---|---|
| 提示文件不存在 | 确认 D2/D3 结果表在 `data/` 下；路径在 CONFIG 区，改成本机实际路径 |
| 重跑没跳过 | 看 `alert_state.json` 的 fingerprint 是否变化；若内容真变了，重发是正确行为 |
| 真发报 business error | webhook 失效或群机器人限制，重试无效——换 webhook；失败态不会写指纹，修好可补发 |
| 演练想切真发却跳过 | 不会——模式纳入指纹，dry/real 指纹不同；若仍跳过说明你改的是打印而非 CONFIG 区的开关 |

代码在本机用真实结果表实测，三步全过：

| 场景 | 实测 | 判定 |
