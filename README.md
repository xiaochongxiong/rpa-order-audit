# 影刀 RPA · 电商订单自动审核 / 对账

> 项目三（已完成）。把人工审单 SOP 改造成「系统自动执行 + 人处理异常」的自动化流程。
> 技术栈：影刀 RPA（社区版/创业版试用）+ Python 代码节点 + Excel + 飞书群机器人。

## 一句话定位

多平台订单进来后，常规单自动放行、异常单隔离处理、账单自动对账、结果留痕告警——**让规则审常规单、人只处理异常**。这是"把人工 SOP 改造成系统自动执行 + 人处理异常"的完整落地。

## 完整链路

```
多平台订单(16单)
    │
    ├─ D2 三态审核分流 ── 自动通过 8 → 待发货
    │                     转人工   5 → 人工队列
    │                     自动拦截 3 → 冻结
    │
    ├─ D3 平台账单对账 ── 平 14 / 金额不符·账单缺单·订单缺单 各1
    │
    └─ D4 异常告警 ────── 11 条异常汇总推飞书 + 指纹幂等防重复
```

## 本项目的独特价值：三方对照实验

同一批 16 单、同一套审核规则，用**三种方式**执行，判定结果 **16/16 完全一致**：

| 执行方式 | 载体 | 证明什么 |
|---|---|---|
| 人手动点 | ERP 教学沙盘（本工作区 `erp-sandbox/`） | 理解业务流程：订单状态怎么流转 |
| RPA 自动点 | 影刀 15 条指令（登录→进审单页→三轮循环点按钮） | 理解 RPA 本质：全程模拟界面、无一条指令碰数据库 |
| Python 直接算 | `docs/D2_自包含代码.py` 读 Excel 判定 | 理解底层逻辑：规则如何落到代码 |

**核心结论**：把业务逻辑和实现方式解耦了——人工点、影刀点界面、代码算表，结果一致。这说明理解的是审单规则本身，而不是某个工具的点击操作。

> ERP 沙盘（`../erp-sandbox/`）是为演示订单全流程自建的教学工具：6 页面模拟真实 ERP（登录→订单→审单→发货→库存→对账→日志），S1–S4 已完成，人手动与影刀自动两条路径都跑通。

## 审核规则（7 条，优先级：拦截 > 转人工 > 通过）

| 级别 | 规则 | 判定 |
|---|---|---|
| 硬违规 | R1 已支付但实付 0 / R2 实付低于成本 / R3 数量超可用库存 | 自动拦截 |
| 软异常 | M1 手机号非 11 位 / M2 地址缺字段 / M3 备注含转寄代收自提 / M4 历史退货≥3 | 转人工 |
| 全不命中 | — | 自动通过 |

一单可命中多条规则但只判一次：先查硬违规（拦截），再查软异常（人工），都没有才放行。

## 技术设计与取舍

### 影刀里的 Python 承载方式（踩坑后定案）

影刀有多种 Python 指令、名字相近但变量机制不同（「插入代码段(Python)」「调用模块」「执行 Python 脚本」在当前版本支持不一）。最终采用**自包含代码**：Python 自己用 `openpyxl` 读 Excel、判定、写结果，影刀里只贴一条「插入代码段(Python)」，**完全绕开变量映射**——这是实测最稳的方案。

### 循环对抗页面刷新（S4b 核心）

审单按钮点击后整页刷新、已审单从列表消失，"抓一次列表循环点"会失效。解法：**条件 XPath + `[1]` 取当前第一个**——`//tr[.//span[contains(text(),'自动通过')]][1]//button[@class='pass']`。点掉一行，下一行自动顶上来成为第一个，循环 8/5/3 次正好审完（实测命中 8/5/3，与预期一致）。这是 RPA 真实工作里"页面刷新导致元素失效"的经典坑。

### 告警幂等（D4 核心）

指纹 = md5(日期 + 模式 + 排序后的异常清单)。重跑指纹相同则跳过推送，防重复轰炸；异常内容变化则自动重发；**推送失败不写指纹**，保证可补发、不漏发。飞书复用项目一 `.env` 的 webhook，沿用四态结果 + 退避重试，失败不崩主流程。

### 其他取舍

- **影刀社区版**：个人非商用免费，指令齐全；社区版无定时触发，用 Windows 任务计划器绕过。
- **自带模拟数据，不接项目一 PG**：项目一只有 SKU 日报指标，无订单粒度字段，无法承担审单。
- **不录屏**：用 README + 公开仓库 + 本文替代演示。

## 业务背景 FAQ

**Q1：电商需要人工审单吗？** 需要，但趋势是"规则审常规单、人只处理异常单"。单量少可人工逐单，多平台/大促时人工跟不上（日均 300 单的小店要切 3 个后台，晚高峰常漏发）。这正是"人工 SOP 改造成系统自动执行+人处理异常"的业务背景。

**Q2：淘宝京东用什么审单？** 分两层——平台自带后台（淘宝/天猫=千牛，京东=京麦，内置基础自动审单）；第三方 ERP（聚水潭、旺店通等，多平台商家几乎都用，订单授权聚合后统一审单、共享库存）。聚水潭/旺店通就是第三方 ERP 的代表。

**Q3：数据在平台手里，RPA 怎么操作？** 三条路径：① API 对接（ERP 走这条，授权后用开放 API 拉单到本地，主流）；② RPA 模拟界面（无 API 时用，拿商家账号登录，人能看到什么它就拿到什么，**不碰数据库、不绕权限**）；③ 手工导出 Excel（最慢最通用）。本项目用本地 Excel 模拟"从 ERP 导出的订单表"——因无真实商家授权，但审核/分流/对账逻辑与真实落地完全一致，只是把"读 Excel"换成"读 ERP 界面"。使用时应说明数据出处。

**Q4：ERP 既然能审单，为什么还要用 RPA 做？** 常见疑问，答案三点：① 很多中小商家没上 ERP，RPA 是零改造成本的自动化；② ERP 覆盖不到跨系统环节（平台下账单、发飞书、写台账），这正是 RPA 主场；③ 对个人而言，项目练的是"审单业务逻辑"，载体用影刀只因门槛低可演示，同一套规则搬到 ERP 配置也成立。核心一句：**审核逻辑是同一套，只是承载方式不同，规则可迁移。**

**Q5：RPA 登录 ERP 还是平台后台？** 看商家现状——上了 ERP 就登 ERP（订单已聚合、审单打单一站式，最常见）；没上 ERP 就登平台后台（千牛/京麦逐单操作）；跨系统任务可能同时登多处。本项目用本地 Excel 把"登录对象"抽象掉了，逻辑链路一致。

**Q6：RPA 是模拟人操作，不用写代码？** 方向对，但表述要准确：对的部分——核心是模拟人在**界面**上操作（点按钮/读表格），不是碰数据库或 API，这是它与 API 对接的根本区别；要补的部分——RPA 底层仍是代码驱动，只是使用者**拖拽指令编排、不写传统程序**，且影刀社区版保留 **Python 代码节点**，复杂逻辑（如对账差异计算）可嵌入 Python。准确说法：**"以模拟界面为主、可视化编排，复杂逻辑嵌 Python 补充。"** `gen_mock_data.py` 就是 Python 节点的应用雏形。

**Q7：企业真的靠导出 Excel 给 RPA 操作吗？** 诚实结论：不是主流，是教学简化。真实生产主流是 API 对接（ERP 授权拉单），其次是 RPA 模拟界面读订单列表，手工导出 Excel 只用于临时分析/对账补数/小商家权宜。本项目用 Excel 是因无真实商家授权，用它代表"从任一系统导出的一张订单表"。**可迁移的是审核规则与分流逻辑，不是"读 Excel"这个动作**——这点要主动说明，否则容易被当成不懂真实业务。

**Q8：有 ERP 的商家，订单操作不是都走 ERP 吗？** 是的，有 ERP 时审单/打单/发货/库存同步都在 ERP 里完成，这是 ERP 核心模块，RPA 不抢这个位置。RPA 的位置是 ERP 覆盖不到的跨系统碎活：平台账单通常要单独下载（对应本项目 D3 对账）、异常汇总发飞书（D4）、无接口的两系统间数据搬运。
